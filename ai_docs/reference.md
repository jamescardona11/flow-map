# App reference

Detail of every part of the app: HTTP routes, files it writes, limits and error codes. To install and use it, the [README](../README.md) is enough.

## Comments, layout and groups

The viewer comments on a screen, or on an area of one, through `/__flowmap/annotations` and `/__flowmap/export` (`src/annotations.ts`). Comments are stored in `temp/annotations.json` in the open map's folder, with the crop of each one in `temp/<id>.png`, in the same format the `/flow-map` skill uses; `GET /__flowmap/export` returns the same text as the skill's `export`, ready to hand to Claude. Creating, editing or deleting requires the `X-Flowmap: 1` header and, if there is an `Origin`, that it be the app's own. The layout and the groups are also stored in the map folder (`src/layout-groups.ts`):
`GET/PUT/DELETE /__flowmap/layout` read, replace and delete `layout.json` (`{"positions": {"<id>": {"x", "y"}}}`, the skill's format; only screens that exist are stored and `PUT` validates everything before writing) and `GET/PUT /__flowmap/groups` read and replace `groups.json` (`{"version": 1, "groups": [{"id", "name", "members": [...]}]}`; a group has 2 to 200 screens and a screen is in at most one group; an empty list deletes the file). Groups go in their own file because the skill rewrites `layout.json` without the keys it does not know: **the skill does not know about groups**. Both are written with a temporary file and a rename, with the same protections as the comments, and the page that saves does not receive the map-changed notice (one from another process does). In the viewer, Shift/⌘-click selects screens, `G` creates a group from them, dragging a screen of a group moves the whole group and "Ungroup" undoes it; "Reset layout" does not delete the groups.

## Route video

Exporting a route as a video needs `ffmpeg` on the PATH (`brew install ffmpeg`); without it the app answers with a clear notice. The "Export route to this screen as video" button in the detail (or `POST /__flowmap-app/export-route {to, from?}`) writes `exports/route-<from>-to-<to>.mp4` in the map folder with the shortest route along the edges, at most 30 screens (`400` if it exceeds that), with a box over the touched area and a crossfade between screens. No subtitles: Homebrew's ffmpeg does not ship `drawtext`.

## Startup, command and window

`npm start` starts the app on port 9999; `PORT=<n> npm start` uses another (for example, for an isolated instance next to yours).

Working map: with no map open, `/` shows the working map, an empty map folder (`<data>/scratch/untitled`) that the app creates with the `init` of this repo's `skill/`. `/choose` always shows the map picker, with the working map first (and creates it if missing, without opening it); it never appears in the recents. If its `map.json` is damaged, the app does not touch it: `/` shows the picker with a notice that states the problem and which folder to delete to start a new one.

To open a map from the terminal: `node src/cli.ts open <folder>` (the path may be relative; `--no-browser` does not open the browser). If the app is already running, the command opens the folder in it; if not, it starts the app in the background and then opens the map. The app announces its port in `app.json` inside `$FLOW_MAP_HOME` while it runs and deletes it when it shuts down. If something goes wrong (a folder that is not a map, the app does not start within 5 s), the command prints it and exits with code 1.

To use Flow Map as an application with its own window: `node src/cli.ts app [<folder>]` starts the app if it is not running (like `open`, through `app.json`) and opens it in its own window, without the browser's toolbar or tabs. It uses the first Chromium-based browser it finds, in this order: Google Chrome, Chromium, Microsoft Edge, Brave and Vivaldi (in `/Applications`), launched with `open -n -a "<browser>" --args --app=http://127.0.0.1:<port>/ --user-data-dir=$FLOW_MAP_HOME/window-profile`. The `window-profile` profile is its own, so the window is independent and does not touch your browser profile. If none is installed, it says so in one line and opens the app in the default browser. With `<folder>`, it opens that map in the app before showing the window.

`node src/cli.ts install-app [--dir <folder>]` creates `Flow Map.app` in the folder (by default `~/Applications`), to open it from Finder, Launchpad or Spotlight like any other app. The bundle is a script that runs `flow-map app` with the absolute paths of `node` and `src/cli.ts` at that moment (and `FLOW_MAP_HOME` if it was set); the icon is generated in code (`src/icon.ts`) and converted to `.icns` with `sips`, which ships with macOS. Reinstalling replaces the previous bundle. **Run `install-app` again if you update or move `node`, or move this repo**: the bundle stores those paths. Limitation: while it runs, the Dock may show the browser's icon (Chrome's app mode); the app's own icon shows in Finder, Launchpad and Spotlight. The window and the bundle exist only on macOS and are not signed.

To link a map to the Claude Code session where you edit it: `node src/cli.ts link <folder>`, run **from inside that session** (it takes the socket and the token from the `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` variables). It stores the link in the app's data directory, `<data>/sessions/<key>.json` (the key is the first 32 hexadecimal characters of the sha256 of the folder's real path), with 600 permissions, and writes nothing to the map folder (not even a `.gitignore`); linking again replaces the previous link. **That file is a credential**: it holds the session token, do not share it. The link lives outside the map folder so that a map folder (which may arrive from git) never carries a token and so that the worker's Read/Edit rules on the folder do not reach it. It does **not** prevent a worker driven by hostile text in a map from copying it with the commands the app lets it run (`flowmap.py ... --image/--tree <any path>` and `npx playwright screenshot file://...` accept paths outside the folder). That residual risk is accepted and bounded by the one-line text rule in the prompts, the approval prompt for everything beyond the allowed rules, and the fact that the worker only runs at the designer's request. An old `session.json` inside the folder that is a link (an object with `version` 1, `socket` and `token`) is deleted when the map is opened and when `link` runs; any other `session.json` is left as it is. The map shows as not linked until you run `link` again. `GET /__flowmap-app/session` says whether the open map is linked (`{ "linked": true, "socket": "<file name>", "alive": true|false }` or `{ "linked": false }`) and never returns the token. `alive` tells whether the socket accepts a connection right now: the app connects and closes without writing anything (1 s timeout). If a variable is missing or the folder is not a usable map, the command prints it, writes nothing and exits with code 1.

## Requests to Claude

Viewer layout (redesign of 2026-11-07): a 48 px bar (← Maps, title, counts, search, Flows, zoom, Connections, Changes, Details), the full-screen canvas, a floating **dock** at the bottom to talk to Claude and a 400 px right panel for the selected screen. The dock has three tabs, "Change the map", "New screen" and "Capture now"; on a map with no screens it opens on "New screen" and the canvas shows a "Start your map" card. While a run is in progress, a card replaces the dock (steps, Cancel and approvals); if it fails it offers "Try again" and "Dismiss". "Re-capture" and "Design contract" are in the right panel. The bar has a "Connections" button (key E) that hides/shows the connections and is remembered per browser.

To ask that session for a change from the app: if the map is linked, the viewer shows the dock ("Change the map" tab: text and a Send button), which does `POST /__flowmap-app/request` with `{ "text": "...", "screen": "<optional id>" }`. The server writes the authentication line and a user message with the text, the map title and the selected screen to the link's socket, and answers `{ "sent": true }`. "Sent" means only that the socket accepted the connection and the two lines were written: the session does not reply, and the app cannot tell whether it held or rejected the message ([`ai_docs/session-socket.md`](session-socket.md)). Errors: `409` if the map is not linked or the session is closed (socket missing, connection refused or no response within 3 s), `400` if the text is empty, exceeds 20,000 characters or the screen does not exist in the map, `403` without `X-Flowmap: 1` or from another origin, and `429` with `Retry-After` if more than 5 requests are accepted in a 10 s window (`requestWindowMs` option of `createServer`). An error body never includes the token.

In the dock the viewer shows a "Session linked" or "Session gone" chip (it queries `/session` every ~10 s, not while the tab is hidden, and right after a `409` on send) and a "How to set this up" button. It reads `GET /__flowmap-app/session-help` (`{ "settings": "<JSON for settings.json>", "steps": ["..."] }`; `404` with no map open), which explains how to set `"crossSessionInbound": "accept"` and `Read`/`Edit` permission rules on the map folder and `Bash` for the skill's commands, without a token or socket path. The app only shows the instructions: it never writes the user's settings ([ADR 0002](adr/0002-the-app-never-touches-claude-settings.md)).

If there is no open session ("Session gone"), the viewer offers the "Run with a new Claude" button: it does `POST /__flowmap-app/request` with `"via": "worker"` (same validation, same headers and same limit of 5 requests per window as requests to the session; it does not need the map to be linked) and the server starts a headless `claude -p` in the map folder (`claude -p <text> --output-format stream-json --verbose --allowedTools <rules>`; the command is the `claudeBin` option, `claude` by default). It answers `202 { "runId": "...", "via": "worker" }`, and `GET /__flowmap-app/runs/<runId>` returns `{ "state": "running" | "needs-approval" | "done" | "failed", "events", "denials"?, "result"?, "error"? }` (`404` if the id does not exist); the viewer polls it every 2 s. **It uses your own Claude Code login**: the app stores no key and does not use `--bare`, and if `ANTHROPIC_API_KEY` is in the environment where the app runs, the child process inherits it and uses it. It only receives the permission rules that "How to set this up" already generates (`Read`/`Edit` on the map folder and `Bash` for the skill's command); everything else is denied without asking, and `--dangerously-skip-permissions` or a permission mode that skips it is never passed. `CLAUDE_CODE_MESSAGING_TOKEN` and `CLAUDE_CODE_MESSAGING_SOCKET` are removed from the child process. Only one run executes at a time (`409` if another is in progress; a rejected one does not spend the request limit), the `workerTimeoutMs` option (10 minutes by default) stops it if it takes too long, closing the app kills the run in progress, and runs live only in memory. To stop a run that is in progress or waiting for a decision, `POST /__flowmap-app/runs/<runId>/cancel` (same guard and same per-map scope as `/decision`) kills it and leaves it as `failed` with "Cancelled by the designer."; the viewer shows a "Cancel" button while it runs. It answers `404` if the id does not exist and `409` if it already finished.

Worker progress and permissions: `events` carries the last 50 entries of what Claude is doing, `{ "kind": "text", "text" }` (up to 300 characters) or `{ "kind": "tool", "name", "summary" }` (command or path, up to 200), and they are already there while the run is still `running`; the viewer shows the last five. If Claude ends because a tool was not allowed (in `-p` it is denied without asking), the run moves to `needs-approval` and keeps the worker's turn; `denials` is `[{ "tool", "summary", "rule" }]`, where `rule` is the minimal rule that would allow exactly that call (`Bash(<exact command>)`, `Read(//<path>)` or `Edit(//<path>)` —also for `Write`—, with the path's special characters escaped, or the tool name if it has no arguments) or `null` if the app cannot offer one (it is not approved from the app). The Claude session id appears in no response. `POST /__flowmap-app/runs/<runId>/decision` (same `X-Flowmap` guard + same origin) accepts `{ "allow": true, "rules": ["<rule>"] }` only for a run in `needs-approval` (`409` if not, `404` if it does not exist) and only with rules that run suggested (`400` if not, without starting anything): it resumes the same conversation with `claude -p "Permission granted for: <rules>…" --resume <session> --allowedTools <the run's rules + the approved ones>`, answers `202 { "runId" }` and the run goes back to `running` with the same id (if it ends with new denials, it goes back to `needs-approval`). `{ "allow": false }` ends it as `done` with "Denied by the designer.", answers `200` and frees the turn. **An approval is valid only for that run**: it is not stored and does not affect others, and the app never changes Claude Code's settings ([ADR 0002](adr/0002-the-app-never-touches-claude-settings.md)). Resuming does not spend the request limit, and the time limit (`workerTimeoutMs`) counts per process and does not run while waiting for the decision. In the viewer, each denial with a rule has a checkbox (unchecked by default) and the buttons "Allow selected and continue" and "Deny".

Attaching comments: `POST /__flowmap-app/request` (to the session or with `"via": "worker"`) accepts `"attach": true`. The message (or the worker's prompt) then carries, after the request text, the same text as `GET /__flowmap/export` (absolute paths of the crops and of the screen included): only the comments of `screen` if given, and those of the whole map if not. If the map has no comments nothing is added and it is not an error; an `attach` that is not a boolean answers `400`. Apart from `attach`, when `screen` is given the message names the absolute path of that screen's full capture (`Full capture of the selected screen: ...`), so Claude can open it with `Read`. No image bytes are attached, only paths. In the dock the "Attach my comments" checkbox comes checked if the map has comments and its state is sent as `attach` both with Send and with "Run with a new Claude".

Requesting a new screen: `POST /__flowmap-app/new-screen` with `{ "title", "description"?, "from"?, "action"?, "via"?: "worker" }` (`src/new-screen.ts`). The app **does not create the screen**: it builds a prompt and delivers it like `/request` (to the linked session, or with `"via": "worker"` to its own `claude -p`; same guard, same limit of 5 per window, same one-run-at-a-time rule and same responses: `{ "sent": true }` or `202 { "runId", "via" }`). The prompt carries the new id (slug of the title, unique in the map with `-2`, `-3`...), the absolute path of the origin screen's capture and of up to 2 neighbours in its flow, the `screens-src/` folder, the viewport size (the origin screen's; otherwise 390x844 on ios/android and 1440x900 on web) and the exact `flowmap.py add` line. Claude writes a self-contained HTML mock in `screens-src/<id>.html`, renders it with `npx playwright screenshot` to `screens-src/<id>.png` and registers it with the skill. Errors: `400` if the title is empty or exceeds 120 characters, the description 4,000, the action 200, `from` does not exist in the map (or its capture is missing) or `via` is not `"worker"`; `403` and `409` as `/request`. Worker runs on this route receive one more rule, `Bash(npx playwright screenshot *)`; **in the linked session the session's own permissions apply**: the terminal may ask you to allow the capture command. In the viewer, the dock's "New screen" tab sends this (with `"via": "worker"` if the chip says "Session gone").

Capturing a new screen now: `POST /__flowmap-app/capture` with `{ "title", "from"?, "action"?, "note"?, "via"?: "worker" }` (`src/capture-new.ts`). As with re-capture, the app **captures nothing**: it builds the prompt (unique new id, platform and how to capture —`agent-device` on mobile, `npx playwright screenshot` on web, asking for the URL if the note does not include it—, absolute path `screens-src/<id>.capture.png`, the exact `flowmap.py add` line with the flow of `from` or that of the entry, and the order not to register it if it is blank, cropped, in error/loading or a duplicate) and delivers it like `/request`, with the same guards, limits and responses. In the viewer, the "Capture it now" button next to "Ask for the screen".

Attaching images: `/request` accepts `"images"`: up to 3 `image/png` or `image/jpeg` data URLs of at most 5 MB each, validated by their real signature. They are stored in `temp/attachments/` of the map folder (with a temporary file and `rename`; a `temp` that is a symbolic link is rejected) and the message or prompt lists their absolute paths so Claude can open them with `Read`; the bytes do not travel in the message. An invalid image answers `400` and neither stores nor delivers anything. In the viewer, pasting an image into the dock shows a thumbnail with a × to remove it; Send and "Run with a new Claude" send it and it is emptied when done.

Requesting a re-capture of a screen: `POST /__flowmap-app/recapture` with `{ "screen": "<id>", "note"?: "<up to 500 characters>", "via"?: "worker" }` (`src/recapture.ts`). As with the new screen, the app **captures nothing**: it builds a prompt and delivers it like `/request` (same guard, same limit of 5 per window, same one-run-at-a-time rule and same responses: `{ "sent": true }` or `202 { "runId", "via" }`). The prompt carries the screen's id and title, the absolute path of its current capture, the map's platform and how to capture according to it (`ios`/`android`: with the `agent-device` CLI on the simulator or emulator, and optionally `--tree` with the tree from `agent-device snapshot`; `web`: with `npx playwright screenshot --viewport-size=<width>,<height>` at the screen's size, asking the designer for the URL if the note does not include it), the designer's note verbatim, the exact line `flowmap.py update <folder> --id <id> --image <folder>/screens-src/<id>.recapture.png` (absolute path; the skill keeps the "before" in `history/` for Before | After) and the order to open the old and the new capture with `Read` and finish with one line reporting the JSON (`changed`, `similarity`). Errors: `400` if `screen` is missing, empty or does not exist in the map, if its capture is missing from the folder, if `note` is not text or exceeds 500 characters or if `via` is not `"worker"`; `403`, `404` and `409` as `/request` (and `404` with no map open). The worker receives the same rules as in "New screen" (folder, `flowmap.py` and `npx playwright screenshot`); **it receives no `agent-device` rules**, so for mobile maps the linked session is preferable, where the session's own permissions apply. In the viewer, the "Re-capture" button in the right panel (with an optional note) appears when the map is linked and a screen is selected.

Design contract and states: a map's design contract (colors, typography, spacing, components) is the `DESIGN.md` file in the map folder; it belongs to the designer and can be committed to git along with the map. `GET /__flowmap-app/design` answers `{ "exists": boolean, "text": string }` (`404` with no map open) and `PUT /__flowmap-app/design` with `{ "text": "..." }` writes it (temporary file and `rename`, same `X-Flowmap` guard and origin as the other writes; `400` if `text` is not text or exceeds 50,000 characters; an empty text deletes the file) and answers `{ "exists": boolean }`. The app does not validate its content. In the viewer, the "Map settings · Design contract" section of the right panel edits it. When it exists, the "New screen" prompt includes it in full under "Design contract of this map" and tells Claude to follow it over copying the neighbours; if it does not exist, it tells Claude there is no contract and to infer the look from the neighbouring captures. The prompt also asks for four states: **one** self-contained HTML in `screens-src/<id>.html` whose state is chosen with `#state=normal|empty|loading|error`, one capture per state (`screens-src/<id>.png` for `normal` and `screens-src/<id>.<state>.png` for the others) and four `flowmap.py add` lines, in order: `normal` with id `<id>` (from the origin screen, as before) and `<id>-empty`, `<id>-loading`, `<id>-error` in the same flow, each with `--from <id> --action "state: <state>"`. Finally, Claude must open each PNG with `Read`, check that it is not blank or cropped, compare the `normal` state with the neighbouring captures and end its reply with a verification report of one line per state.

## Captures, HTML screens and history

Copying the selected screen's capture: in a screen's detail, the "Copy screenshot" button puts its capture on the clipboard as `image/png` (a JPEG is converted with a canvas), ready to paste into Claude. If the browser blocks the clipboard, the viewer shows the capture's absolute path with a "Copy path" button (and, if it cannot copy text either, the path is left selectable), because Claude Code can read a path with `Read`. The path comes from `GET /__flowmap-app/capture-path?screen=<id>`, which answers `{ "path": "<absolute real path>" }` (`src/capture-path.ts`); `404 { "error" }` with no map open and `400 { "error" }` if `screen` is missing, does not exist in the map or its capture is not on disk. A capture whose `image` leaves the map folder (`../x.png` or a symbolic link pointing outside) is treated as nonexistent: `/request` with `screen`, `/new-screen` (`from`) and `/recapture` answer `400` and deliver nothing, and neighbours that leave the folder are omitted from the "New screen" prompt. Only the screen's capture is copied, not a region of the map.

HTML screens: a screen that Claude laid out as HTML has **two files**: the HTML (the source, self-contained: CSS, JS and data inline, no network) and its rendered PNG, which remains the `image` in `map.json` so that the canvas, the comments, Before | After and the thumbnails work the same as with any capture. The screen also carries the optional field `"html": "screens-src/<id>.html"` (a path relative to the map folder that ends in `.html`; additive, `version` stays at 1). `src/map-check.ts` validates it: if it is not text, is absolute, has a `..` segment or does not end in `.html`, the map is not usable (`400` when opening it, and the reason names the screen); a screen without `html` does not change. In the detail, a screen with `html` shows the "Capture | HTML" button (Capture by default): HTML shows it live in an `<iframe sandbox="allow-scripts">` (never `allow-same-origin`), scaled to the capture's box, with the note "Live HTML. Comments and Before|After use the capture."; when comparing or commenting it goes back to the capture, and if the file cannot be served it shows "HTML not available". The server serves `.html` only from `screens/` and `screens-src/` (in `thumbs/`, `history/` and `baselines/` it answers `404`) with `Content-Security-Policy: sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; font-src data:; media-src data:`, `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`: the CSP `sandbox` makes the document an opaque origin with no network, so that even opening it directly in a tab it cannot reach the app's endpoints. Every file the app serves (captures too) is checked with `realpath`: a symbolic link that leaves the map folder answers `404`. The viewer does not watch the `screens-src/` folder for live reload (the reload is triggered by the `map.json` that `flowmap.py add` updates); editing the HTML and rendering the PNG from the app, and `add --html` in the skill, are out of scope here.

History of a screen: the skill must save **every** previous capture of a screen as `history/<id>/<YYYYMMDDTHHMMSSZ>.<png|jpg|jpeg>`, where the name is the compact UTC time at which that capture was taken (if two fall in the same second, the later one carries `-2`, `-3`... before the extension). The app only reads that convention (`src/history.ts`), never writes or prunes the history; as long as the skill keeps saving a single "before" in `history/<id>.png`, that file does not count as a version and no screen shows history. `GET /__flowmap-app/history?screen=<id>` answers `{ "versions": [{ "capturedAt", "image", "current" }] }`, newest first: the first is the current capture from `map.json` (`current: true`) and it is followed by the files in `history/<id>/` with a valid name (other files, subfolders and symbolic links that leave the folder are ignored). `GET /__flowmap-app/changes` answers `{ "events": [{ "screen", "title", "capturedAt", "image", "current" }] }`: all versions of all screens, newest first (those without a date, at the end and in map order), with a maximum of 200. All dates come out in UTC ISO with `Z` and no milliseconds (`2026-10-29T12:23:17Z`); a missing or unreadable one is `null`. Both give `404 { "error" }` with no map open and `400 { "error" }` (the first) if `screen` does not exist; images are served through `/history/<id>/<file>` with the same `realpath` check as the rest. In the detail, the "History" row (only if there is more than one version) shows a button per version with its date, viewing an old version uses the "before" slot and "Compare with current" puts it next to the current one; the header's "Changes" button lists all captures with a thumbnail and opens the screen (and that version if it is not the current one).

Recent maps are stored in `recents.json` inside `$FLOW_MAP_HOME` (by default `~/.flow-map`).

`src/viewer/viewer.html` is a copy of the `/flow-map` skill's viewer, taken on 2026-11-05. From then on it evolves on its own: changes to the skill's viewer do not arrive by themselves ([ADR 0001](adr/0001-app-and-skill-are-separate.md)).
